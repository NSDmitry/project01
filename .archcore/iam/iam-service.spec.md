## Purpose & Scope
Нормативный контракт бизнес-логики IAM: `AuthService`, `UserService`, `UserSessionService` (@app/iam/service.py). Потребители - @app/iam/router.py, @app/iam/deps.py (авторизация всех остальных доменов) и @app/iam/tasks.py (cron-очистка). Вне scope: HTTP-коды и rate limiting (спек роутера), SQL-слой (спек репозитория).

## Surface
- `AuthService`: `register`, `login`, `check_login_available`, `login_with_telegram`, `logout`, `change_password`, `delete_current_user`, `validate_password_policy` - @app/iam/service.py.
- `login` принимает IP клиента (как и `register`) - без него невозможна блокировка перебора по случайным номерам.
- `UserSessionService`: `create_user_session`, `get_user_session`, `logout_user_session`, `logout_all_user_sessions`, `cleanup_idle_sessions`.
- `get_user_session` возвращает сессию либо отказывает; пустого результата в контракте нет.
- `UserService`: `get_user_by_id`, `update_user_info`, `update_avatar`, `validate_phone_number`.
- Константы: `MAX_SESSIONS_PER_USER = 5`, `SESSION_MAX_IDLE = 30 дней`, `LAST_USED_THRESHOLD = 5 минут`.
- Зависимости: эскалирующая блокировка @app/iam/brute_force.py с двумя политиками (по номеру телефона и по IP), подпись Telegram @app/iam/security/telegram.py, событийная шина @app/core/events.py, хранилище картинок @app/core/media.py.

## Normative Behavior
1. WHEN вызывается `register`, сервис MUST проверить лимит регистраций с IP до создания пользователя (@app/core/rate_limit.py).
2. WHEN вызывается `register` или `change_password`, сервис MUST проверить пароль по policy: длина 8-128, хотя бы одна заглавная, одна строчная, одна цифра, без ведущих/замыкающих пробелов.
3. Сервис MUST хешировать пароль bcrypt в отдельном потоке (`asyncio.to_thread`) - bcrypt блокирует event loop.
4. WHEN `login` получает несуществующий номер или неверный пароль, сервис MUST вернуть один и тот же ответ Unauthorized (анти-enumeration).
5. WHEN попытка входа неудачна, сервис MUST зарегистрировать её в обеих блокировках - по номеру телефона и по IP, - включая случай несуществующего номера; WHEN вход успешен, сервис MUST сбросить только счётчики по номеру телефона.
6. WHEN вызывается `login`, сервис MUST проверить блокировку по IP до обращения к БД и до сверки пароля - иначе блокировка становится оракулом (по коду ответа видно попадание в пароль).
7. WHEN вызывается `login_with_telegram`, сервис MUST проверить HMAC-подпись initData и возраст `auth_date` (не старше 1 часа) до обращения к БД.
8. WHEN Telegram-пользователь входит впервые, сервис MUST создать запись User по `telegram_id` без пароля.
9. WHEN создаётся сессия, сервис MUST выдать `sid = secrets.token_urlsafe(32)` и сохранить только его SHA-256-хеш.
10. WHEN создаётся сессия сверх лимита 5 на пользователя, сервис MUST удалить самые старые сессии сверх лимита.
11. WHEN `get_user_session` находит сессию с `last_used` старше 5 минут, сервис MUST обновить `last_used`; чаще - MUST NOT (экономия записей).
12. WHEN вызывается `change_password`, сервис MUST подтвердить текущий пароль и завершить все активные сессии пользователя после смены.
13. WHEN вызывается `delete_current_user`, сервис MUST опубликовать событие USER_DELETED с флагами `delete_clubs`/`delete_threads`/`delete_comments` до удаления пользователя, затем удалить пользователя, все его сессии и файл его аватара - аватар это контент пользователя, и вместе с аккаунтом уходит и он.
14. WHEN вызывается `update_avatar`, сервис MUST сохранить картинку в хранилище (проверка типа и размера - @app/core/media.py), записать ключ файла пользователю и удалить прежний файл: без удаления хранилище растёт с каждой загрузкой. Ссылка на аватар в ответе MUST собираться из ключа - в БД URL не хранится.

## Constraints & Invariants
- Инвариант: сырой `sid` нигде не сохраняется - в БД только SHA-256-хеш.
- Инвариант: у пользователя не больше 5 живых сессий.
- Инвариант: iam не импортирует модули bookclubs/threads - очистка чужих данных только через событие USER_DELETED.
- Инвариант: у пользователя не больше одного аватара - новая загрузка заменяет прежнюю, а не добавляет вторую.
- Ограничение: неудачные подтверждения пароля (change_password, delete) идут только в блокировку по номеру телефона, не в блокировку по IP, - иначе украденная сессия позволяет перебирать пароль в обход блокировки, но опечатки владельца в собственном пароле не должны блокировать чужие входы с того же адреса.
- Ограничение: счётчик по IP намеренно не сбрасывается успешным входом - иначе атакующий с одним валидным аккаунтом обнуляет счётчик перед каждым порогом.
- Инвариант: уровень эскалации живёт не меньше самого длинного блока своей политики - иначе он протухает при живом блоке и следующая серия неудач понижает уже выданный блок.
- Инвариант: порог блокировки срабатывает ровно на одной неудачной попытке из серии - параллельные попытки не должны перескакивать уровни эскалации.
- Инвариант: подтверждение пароля ключуется номером телефона, поэтому применимо только к аккаунту, у которого есть и номер, и пароль. Аккаунт без номера не должен попадать в общий счётчик попыток вместе с другими такими же аккаунтами.
- Ограничение: старый файл аватара удаляется до коммита транзакции. Упавший коммит оставит ссылку на удалённый файл - принято сознательно: альтернатива (не удалять никогда) даёт неограниченный рост хранилища.

## Failure Behavior
1. IF номер уже занят, THEN `register`/`update_user_info` MUST выбросить Conflict.
2. IF номер телефона заблокирован эскалацией (5 неудач: блок 60 с, далее 30 мин, далее 24 ч), THEN сервис MUST выбросить TooManyRequests с оставшимся TTL; попытки во время блока идут в счёт эскалации.
3. IF IP заблокирован эскалацией (20 неудач: блок 5 мин, каждые следующие 20 - 24 ч), THEN сервис MUST выбросить TooManyRequests с оставшимся TTL; попытки во время блока идут в счёт эскалации. Счётчик неудач по IP накапливается в окне 1 часа.
4. IF наступила любая из двух блокировок, THEN ответ MUST быть неотличим по признаку блокировки - тело 429 не сообщает, сработал номер или адрес.
5. IF сессии с таким `sid` нет, THEN `get_user_session` MUST выбросить Unauthorized и MUST NOT возвращать отсутствие отдельным значением: трактовка единственная и одинакова для всех вызывающих (см. @.archcore/conventions/domain-errors.rule.md, правило 5). Отказ MUST быть неотличим от отказа по истечению.
6. IF сессия не использовалась дольше 30 дней, THEN `get_user_session` MUST выбросить Unauthorized с errors=["session_expired"].
7. IF подпись Telegram неверна, отсутствует или initData старше 1 часа, THEN сервис MUST выбросить Unauthorized. То же относится к разобранным данным пользователя, которые не являются объектом или не содержат идентификатор, - подделанный payload MUST давать отказ авторизации, а не внутреннюю ошибку.
8. IF у аккаунта нет пароля (Telegram-only), THEN `change_password` MUST выбросить BadRequest, а `delete_current_user` MUST пропустить подтверждение пароля. Само подтверждение пароля MUST независимо отказывать аккаунту без номера телефона или без пароля - вызывающий не обязан быть единственной защитой.
9. IF Redis не сконфигурирован (тесты), THEN блокировки и лимиты MUST деградировать в no-op, не ломая вход. Случай "Redis сконфигурирован, но недоступен" контрактом не покрыт: вход завершается ошибкой 500.
10. IF загруженный файл аватара больше лимита или его содержимое не поддерживаемое изображение, THEN `update_avatar` MUST отказать до записи в БД и хранилище (PayloadTooLarge / UnsupportedMediaType).

## Conformance
Реализация конформна, когда выполняет поведения 1-14, держит инварианты (хеш-only sid, лимит сессий, отсутствие импортов чужих доменов, единственный аватар, живучесть уровня эскалации, срабатывание порога ровно один раз, ключевание подтверждения пароля номером) и правила отказов 1-10. Проверяется тестами tests/sso_tests/, tests/users/ и tests/media/test_image_uploads.py.
