## Purpose & Scope
Контракт слоя хранения bookclubs: `BookClubRepository` и `ReadingRepository` (@app/bookclubs/repository.py). Потребители - @app/bookclubs/service.py, порт `ClubsPort` домена threads (`get_book_club`, `is_member`), порт `ReadingsPort` домена threads (`get_stage_club_id`) и обработчики событий. Вне scope: резолв жанров, владельцев и книг (спек сервиса).

## Surface
- CRUD: `create_book_club`, `get_book_clubs`, `get_book_club`, `update_book_club`, `delete_book_club`.
- Участие: `is_member`, `get_members`, `add_member`, `remove_member`.
- Роли и владение: `get_role`, `set_role`, `transfer_ownership`.
- Приглашения: `create_invite`, `get_invite`.
- Заявки: `upsert_join_request`, `get_join_request`, `get_pending_join_requests`, `resolve_join_request`.
- Жанры: `set_genres`, `get_genre_ids`, `handle_genres_deleted`.
- События: `handle_user_deleted`, `change_threads_count`.
- Заходы (`ReadingRepository`): `create_reading`, `get_reading`, `get_active_readings`, `get_readings`, `finish_reading`, `get_stages`, `get_stage_club_id`, `set_progress`, `get_progress`, `get_progress_page`, `get_expected_positions`, `count_on_track`.
- Модели: `BookClub`, `ClubMember`, `ClubInvite`, `ClubJoinRequest`, `BookClubGenre`, `Reading`, `ReadingStage`, `ReadingProgress` - @app/bookclubs/models.py.

## Normative Behavior
1. WHEN создаётся клуб, репозиторий MUST в одной транзакции создать клуб, добавить владельца в участники, привязать жанры и завести счётчик участников равным единице.
2. `get_book_clubs` MUST поддерживать фильтры: `relation=owner` (owner_id), `relation=member` (подзапрос по club_members), набор жанров (подзапрос по book_club_genres) и полнотекстовый поиск по названию и описанию. Фильтры MUST совмещаться по И, результат - `(items, total)`. Режим приватности клуба MUST NOT участвовать в фильтрации: закрытый клуб остаётся находимым, иначе в него нельзя было бы попроситься.
3. Полнотекстовый поиск MUST идти по генерируемому столбцу `search_vector`, а не по подстроке. Каждое слово запроса MUST искаться по префиксу: подстрочный ILIKE находил неполное слово внутри полного, и без префикса такой запрос был бы потерян. Совпадение в середине слова при этом не находится - осознанная плата за словоформы и ранжирование.
4. Строка tsquery MUST собираться только из словесных символов запроса пользователя. Операторы tsquery (`& | ! ( ) : *`) MUST отбрасываться, а не экранироваться: иначе запрос пользователя либо валится с ошибкой разбора, либо подмешивает в поиск чужой оператор (например отрицание).
5. Порядок выдачи MUST быть по убыванию `ts_rank`, если задан поисковый запрос, и по `id` иначе. `id` MUST быть последним ключом сортировки всегда: без тай-брейка строки с равным рангом могут повторяться на соседних страницах.
6. `delete_book_club`, `set_genres` и `update_book_club` MUST проверять владельца через `require_permission` до изменения.
7. `set_genres` MUST заменять набор жанров целиком (delete + insert).
8. `update_book_club` MUST применять только переданные поля (название, описание, режим приватности) и оставлять непереданные без изменений; жанры и состав участников MUST оставаться нетронутыми.
9. `get_members` MUST отдавать только страницу участников клуба вместе с их ролью. Общее число участников репозиторий не считает - его держит `BookClub.members_count`.
10. WHEN меняется состав участников (создание клуба, вступление, выход, исключение, удаление пользователя), репозиторий MUST в той же транзакции обновить `members_count` атомарным UPDATE с `GREATEST(members_count + delta, 0)`. Приращение MUST считать БД, а не Python: чтение-изменение-запись теряет параллельные изменения состава одного клуба.
11. WHEN приходит USER_DELETED с `delete_clubs=true`, `handle_user_deleted` MUST удалить клубы владельца и вернуть их id (для CLUBS_DELETED); при `false` - занулить `owner_id`; членство и заявки пользователя MUST удаляться всегда, а счётчики затронутых клубов - уменьшаться до удаления строк членства.
12. `change_threads_count` MUST менять счётчик атомарным UPDATE с `GREATEST(threads_count + delta, 0)` - защита от ухода в минус при дублях событий (at-least-once доставка).
13. Репозиторий MUST завершать записи `flush`, а не `commit` - транзакцию держит session dependency.
14. `get_role` MUST отдавать роль из строки членства либо пустое значение, если пользователь не состоит в клубе. Владельца эта роль не описывает: владение читается из `owner_id` клуба.
15. `transfer_ownership` MUST в одной транзакции сменить владельца и сбросить роль нового владельца в `member` - иначе оставленная роль модератора стала бы вторым источником правды о его правах. Прежний владелец MUST остаться участником клуба с ролью `member`: членства он не терял, а модератором его никто не назначал.
16. `create_invite` MUST генерировать код криптостойким источником случайности, а не предсказуемой последовательностью: код и есть единственный секрет, дающий вход в закрытый клуб.
17. `upsert_join_request` MUST быть upsert-ом по паре (клуб, пользователь): повторная подача MUST возвращать заявку в статус ожидания, а не падать об уникальный ключ и не заводить вторую строку. Проверка с последующей вставкой недопустима: две параллельные заявки одного пользователя прошли бы её обе.
18. `get_pending_join_requests` MUST отдавать только заявки в статусе ожидания и их общее число - рассмотренные заявки в очереди не показываются.
19. `create_reading` MUST создавать заход и его этапы в одной транзакции, а позиции этапов MUST расставляться по порядку присланного списка, начиная с единицы. Клиент номера этапов не задаёт.
20. Чтение захода MUST идти запросом, а не выдачей объекта из identity map: книга подтягивается загрузчиком при выполнении SELECT, а уже загруженный объект вернулся бы без неё.
21. `set_progress` MUST быть upsert-ом по паре (заход, участник): повторная отметка MUST переписывать строку, а не падать об уникальный ключ и не заводить вторую. `updated_at` MUST выставляться явно - ORM-хук onupdate на пути INSERT ... ON CONFLICT не срабатывает.
22. `get_expected_positions` MUST отдавать максимальную позицию этапа, чья дата уже наступила, по каждому заходу; заход без наступивших этапов в результате MUST отсутствовать - сверять прогресс ещё не с чем.
23. `count_on_track` MUST считать участников, чей закрытый этап не ниже ожидаемого, одним запросом на все заходы страницы (группировка по заходу и позиции), а не запросом на заход.
24. WHEN участник выходит из клуба, исключается или удаляется пользователь, репозиторий MUST удалить его строки прогресса: иначе доля участников в графике считается от числа участников, а числитель включает ушедших.

## Constraints & Invariants
- Инвариант: участник уникален на пару (club_id, user_id) - составной PK club_members; повторное добавление ловится IntegrityError.
- Инвариант: владелец клуба хранится только в `book_clubs.owner_id`; `club_members.role` принимает лишь `member` и `moderator` (CHECK), поэтому владение и роль разъехаться не могут.
- Инвариант: режим приватности клуба принимает только `public`, `by_request`, `by_invite`, а статус заявки - `pending`, `approved`, `rejected`; допустимые значения держит CHECK в БД, а не только валидация запроса.
- Инвариант: код приглашения уникален глобально - по нему вступают, не зная id клуба.
- Инвариант: имя клуба уникально (unique constraint на name).
- Инвариант: `search_vector` - генерируемый столбец: его считает СУБД при записи в название и описание. Код MUST NOT писать в него и MUST NOT поддерживать его событиями или триггерами; рассинхрон текста и индекса поиска поэтому невозможен по построению.
- Инвариант: конфигурация текстового поиска подставляется в запрос литералом, а не bind-параметром - тип regconfig драйвер не передаёт. Сам текст запроса пользователя MUST оставаться bind-параметром.
- Инвариант: `members_count` равен числу строк club_members этого клуба. В отличие от `threads_count` счётчик ведётся не событиями, а в одной транзакции с самим членством, поэтому разъехаться может только при правках в обход репозитория.
- Инвариант: UPDATE счётчика MUST помечать уже загруженный объект клуба просроченным (`synchronize_session="fetch"`) - иначе следующий `get_book_club` в той же сессии отдаст его из identity map со старым значением.
- Инвариант: фильтр по `relation` осмыслен только вместе с пользователем - оба параметра опциональны по отдельности, но `relation` без пользователя недопустим.
- Инвариант: изменения атрибутов загруженной модели фиксируются `flush`, а не `refresh` - сессия создаётся с `autoflush=False`, поэтому `refresh` перечитал бы строку и молча затёр несохранённые правки.
- Инвариант: единственность незакрытого захода у клуба держит частичный уникальный индекс, а не предварительная проверка: два параллельных создания прошли бы SELECT оба.
- Инвариант: заходы, этапы, прогресс, приглашения и заявки удалённого клуба уносит каскад БД по club_id - кода для этого нет.

## Failure Behavior
1. IF имя клуба занято, THEN `create_book_club` и `update_book_club` MUST откатить и выбросить Conflict.
2. IF пользователь уже состоит в клубе, THEN `add_member` MUST откатить и выбросить Conflict, счётчик участников MUST остаться прежним.
3. IF удаляемого членства нет, THEN `remove_member` MUST выбросить Conflict.
4. IF клуб не найден, THEN `get_book_club` MUST выбросить NotFound.
5. IF задан `relation`, но не передан пользователь, THEN `get_book_clubs` MUST выбросить ошибку, а не игнорировать фильтр - молчаливый пропуск вернул бы вызывающему весь каталог клубов вместо его собственных.
6. IF в запросе нет ни одного словесного символа, THEN поиск MUST вырождаться в отсутствие текстового фильтра, а не в пустую выдачу.
7. IF роль назначается тому, кто не состоит в клубе, THEN `set_role` MUST выбросить NotFound - молчаливый UPDATE нуля строк выглядел бы как успех.
8. IF новый владелец не состоит в клубе, THEN `transfer_ownership` MUST выбросить UnprocessableEntity и не менять владельца.
9. IF кода приглашения нет, THEN `get_invite` MUST выбросить NotFound.
10. IF заявка не найдена, THEN `get_join_request` MUST выбросить NotFound; IF заявка уже рассмотрена, THEN `resolve_join_request` MUST выбросить Conflict и оставить статус прежним.
11. IF у клуба уже есть незакрытый заход, THEN `create_reading` MUST откатить и выбросить Conflict.
12. IF заход не найден, THEN `get_reading` MUST выбросить NotFound.
13. IF заход уже закрыт, THEN `finish_reading` MUST выбросить Conflict, а дата закрытия MUST остаться прежней.

## Conformance
Реализация конформна, когда выполняет поведения 1-24, держит инварианты уникальности, единственного источника владения, генерируемого столбца, счётчика участников и единственного незакрытого захода и правила отказов 1-13. Проверяется тестами tests/bookclubs/ и tests/readings/.
