## Purpose & Scope
Контракт бизнес-логики bookclubs: `BookClubService` и `ReadingService` (@app/bookclubs/service.py). Потребители - @app/bookclubs/router.py и обработчики событий. Вне scope: HTTP-коды (спек роутера), SQL (спек репозитория).

## Surface
- `BookClubService`: `create_book_club`, `get_book_clubs`, `search_book_clubs`, `get_book_club`, `get_members`, `update_book_club`, `delete_book_club`, `join`, `leave`, `set_genres`, `create_invite`, `join_by_invite`, `request_join`, `get_join_requests`, `resolve_join_request`, `set_member_role`, `remove_member`, `transfer_ownership`.
- `ReadingService`: `create_reading`, `get_current_reading`, `get_readings`, `finish_reading`, `set_progress`, `get_progress`.
- Кросс-доменные зависимости - только порты `GenresPort`, `UsersPort`, `BooksPort` (@app/bookclubs/ports.py) и события @app/core/events.py.

## Normative Behavior
1. WHEN создаётся клуб или заменяются жанры, сервис MUST проверить каждый код жанра через `GenresPort.get_by_codes`; дубли кодов MUST схлопываться до уникальных.
2. WHEN клуб удалён, сервис MUST опубликовать CLUBS_DELETED с `club_ids` - треды удалённого клуба чистит домен threads (FK нет).
3. WHEN собирается ответ, сервис MUST подтягивать владельца через `UsersPort.get_summaries_by_ids` и жанры через `GenresPort.get_by_ids` батчем на всю страницу (не N+1); owner и genres в модели не живут, клуб хранит только id. Заявители в очереди заявок MUST подтягиваться тем же батчем.
4. Жанры клуба в ответе MUST идти в порядке `sort_order` каталога жанров.
5. WHEN в запросе поиска переданы коды жанров, сервис MUST превратить их в id тем же путём, что и при создании клуба (`GenresPort.get_by_codes`), и передать id в репозиторий как фильтр. Свободный текст запроса по жанрам MUST NOT искаться: жанр сужает выдачу, а не расширяет её.
6. WHEN обновляются название, описание и режим приватности клуба, сервис MUST отдавать ту же модель ответа, что и остальные операции над клубом - с владельцем, жанрами и счётчиками.
7. `members_count` в ответе и `total` страницы участников MUST браться из столбца загруженного клуба. Сервис MUST NOT считать участников агрегатом: стоимость такого счёта росла с размером клуба, а не страницы, и на каталоге умножалась на число клубов страницы.
8. Карточка клуба MUST содержать текущий заход - книгу, дедлайн и долю участников в графике - либо пустое значение, если клуб ничего не читает. Данные захода MUST собираться батчем на всю страницу клубов, как владелец и жанры.
9. Режим приватности клуба определяет только способ вступления и MUST NOT влиять на видимость клуба в каталоге, поиске и карточке: клуб «по заявке» иначе нельзя было бы найти, чтобы подать заявку.
10. Свободное вступление MUST быть доступно только в клубе с режимом `public`. В клуб `by_request` вступают через одобренную заявку, в клуб `by_invite` - по коду приглашения.
11. Код приглашения MUST давать вход независимо от режима приватности клуба: иначе он был бы бесполезен именно там, где он нужен. Просроченный код MUST перестать действовать.
12. У клуба MUST действовать не более одного кода приглашения: создание нового MUST гасить прежние. Это единственный механизм отзыва - без него исключённый участник возвращается по коду, который остался у него на руках, а отобрать код нечем.
13. Заявка MUST приниматься только клубом с режимом `by_request` и только от того, кто в клубе не состоит. Повторная подача после отказа MUST возвращать заявку в очередь как новую: с новым временем подачи и в конец очереди, а не на место первой попытки.
14. Одобрение заявки MUST делать заявителя участником клуба. IF заявитель уже стал участником другим путём (например по приглашению), THEN одобрение MUST завершиться успешно, не добавляя его повторно.
15. Заявка MUST адресоваться парой (клуб, идентификатор заявки): заявка другого клуба для этого клуба не существует.
16. Роль пользователя в клубе MUST выводиться так: владелец - тот, кто указан владельцем клуба; остальные - по роли в своей строке членства. Роль владельца в строке членства MUST NOT храниться.
17. Приглашения, очередь заявок, рассмотрение заявок и исключение участников MUST быть доступны владельцу и модераторам клуба. Назначение ролей и передача владения MUST быть доступны только владельцу: иначе модератор наплодил бы себе равных или увёл клуб.
18. Администратор MUST иметь права владельца в любом клубе - той же проверкой, что и остальные операции владельца.
19. Модератор MUST NOT исключать другого модератора. Владелец MUST оставаться в составе клуба, пока он владелец: его нельзя ни исключить, ни выйти самому. Оба пути MUST упираться в один и тот же запрет - иначе состав терял бы владельца через соседнюю ручку, а права по владению оставались бы при нём.
20. Передача владения MUST быть возможна только участнику клуба. Прежний владелец MUST оставаться участником, новый MUST терять роль модератора, если она была.
21. WHEN создаётся заход, книга MUST резолвиться через `BooksPort.get_or_create_book` по тому же идентификатору тома, что и у тредов: повторный выбор той же книги MUST переиспользовать запись.
22. Создавать и закрывать заход MUST только владелец клуба (или админ). На модераторов это право пока не распространяется - они управляют составом клуба, а не его чтением.
23. Отмечать прогресс MUST только участник клуба и только пока заход не закрыт. Отметка MUST заменять прогресс целиком: прислан этап - фиксируется он, прислана только страница - закрытым считается последний этап, чья последняя страница уже прочитана.
24. Участник считается в графике, когда его закрытый этап не ниже последнего этапа, чей срок уже наступил. WHILE ни один срок не наступил, в графике MUST считаться все участники клуба, включая не отметивших ничего - отставать не от чего.
25. Доля участников в графике MUST считаться от числа участников клуба, а не от числа отметившихся, и MUST NOT превышать единицу.
26. Сводка текущего захода MUST содержать этап, который должен быть закрыт к сегодняшнему дню; пока ни один срок не наступил - пустое значение.

## Constraints & Invariants
- Инвариант: сервис не импортирует модули iam/genres/threads напрямую - только порты и события.
- Инвариант: `threads_count` клуба - денормализованный столбец, изменяется только обработчиками событий THREAD_CREATED/THREAD_DELETED, не пользовательскими операциями.
- Инвариант: `members_count` - тоже денормализованный столбец, но своего домена: его ведёт репозиторий в одной транзакции с club_members, событий для него нет.
- Инвариант: у клуба ровно один владелец, он же всегда участник, и роль владельца - производная от владения, а не отдельная запись.
- Инвариант: название, описание и режим приватности клуба редактируются только владельцем и только через `update_book_club`; жанры - отдельной операцией `set_genres`.
- Инвариант: любое изменение состава клуба (вступление, вступление по коду, одобрение заявки, выход, исключение) проходит через один и тот же путь добавления и удаления участника - счётчик участников и чистка прогресса поэтому не могут разойтись между способами.
- Инвариант: текущий заход у клуба один; следующий можно завести только после закрытия предыдущего.
- Инвариант: доля участников в графике - производная величина, она нигде не хранится и считается на чтение из этапов и отметок.

## Failure Behavior
1. IF среди кодов жанров есть неизвестный, THEN сервис MUST выбросить UnprocessableEntity с перечнем неизвестных кодов. Это правило распространяется и на коды жанров в запросе поиска: неизвестный код - ошибка, а не молча пустая выдача.
2. IF клуб не найден, THEN сервис MUST пробросить NotFound репозитория.
3. IF `owner_id` клуба NULL (владелец удалил аккаунт без удаления клубов), THEN ответ MUST содержать `owner = null`. Такой клуб через API нельзя удалить, отредактировать, передать и раздать в нём роли - проверка владельца не проходит ни для кого, кроме администратора. Принятое ограничение: восстановление владения - операция администратора, и передача клуба существует ровно для того, чтобы владелец не доводил до этого состояния.
4. IF свободное вступление в клуб с закрытым режимом, THEN сервис MUST выбросить Forbidden с указанием способа вступления, а не Conflict: вступление отклонено правами, а не состоянием.
5. IF код приглашения неизвестен или уже погашен новым, THEN NotFound; IF срок его действия истёк, THEN Forbidden.
6. IF заявка подана в клуб, который заявок не принимает, или подана участником клуба, THEN Conflict.
7. IF заявка уже рассмотрена, THEN повторное решение MUST вернуть Conflict; IF заявка принадлежит другому клубу, THEN NotFound.
8. IF роль меняет не владелец, THEN Forbidden; IF роль назначается владельцу клуба, THEN UnprocessableEntity - роль владельца меняется только передачей клуба; IF адресат роли не состоит в клубе, THEN NotFound.
9. IF исключает не владелец и не модератор, THEN Forbidden; IF модератор исключает модератора, THEN Forbidden; IF исключаемый - владелец или владелец выходит сам, THEN Forbidden с указанием передать клуб; IF исключаемый не состоит в клубе, THEN Conflict.
10. IF клуб передаётся не владельцем, THEN Forbidden; IF новый владелец не состоит в клубе, THEN UnprocessableEntity.
11. IF у клуба нет незакрытого захода, THEN запрос текущего захода MUST вернуть NotFound, а не пустую сводку.
12. IF присланный этап принадлежит другому заходу, THEN отметка прогресса MUST вернуть NotFound.
13. IF прогресс отмечает не участник клуба, THEN сервис MUST выбросить Forbidden; IF заход уже закрыт, THEN Conflict.

## Conformance
Реализация конформна, когда выполняет поведения 1-26, держит инварианты портов, единственного владельца в составе клуба, обоих счётчиков, единого пути изменения состава и единственного текущего захода и правила отказов 1-13. Проверяется тестами tests/bookclubs/ и tests/readings/.
