## Purpose & Scope
Контракт бизнес-логики bookclubs: `BookClubService`, `ReadingService` и `NominationService` (@app/bookclubs/service.py). Потребители - @app/bookclubs/router.py и обработчики событий. Вне scope: HTTP-коды (спек роутера), SQL (спек репозитория).

## Surface
- `BookClubService`: `create_book_club`, `get_book_clubs`, `search_book_clubs`, `get_book_club`, `get_members`, `update_book_club`, `delete_book_club`, `join`, `leave`, `set_genres`.
- `ReadingService`: `create_reading`, `get_current_reading`, `get_readings`, `finish_reading`, `set_progress`, `get_progress`.
- `NominationService`: `nominate`, `get_nominations`, `vote`, `unvote`, `close_voting`.
- Кросс-доменные зависимости - только порты `GenresPort`, `UsersPort`, `BooksPort` (@app/bookclubs/ports.py) и события @app/core/events.py.

## Normative Behavior
1. WHEN создаётся клуб или заменяются жанры, сервис MUST проверить каждый код жанра через `GenresPort.get_by_codes`; дубли кодов MUST схлопываться до уникальных.
2. WHEN клуб удалён, сервис MUST опубликовать CLUBS_DELETED с `club_ids` - треды удалённого клуба чистит домен threads (FK нет).
3. WHEN собирается ответ, сервис MUST подтягивать владельца через `UsersPort.get_summaries_by_ids` и жанры через `GenresPort.get_by_ids` батчем на всю страницу (не N+1); owner и genres в модели не живут, клуб хранит только id.
4. Жанры клуба в ответе MUST идти в порядке `sort_order` каталога жанров.
5. WHEN в запросе поиска переданы коды жанров, сервис MUST превратить их в id тем же путём, что и при создании клуба (`GenresPort.get_by_codes`), и передать id в репозиторий как фильтр. Свободный текст запроса по жанрам MUST NOT искаться: жанр сужает выдачу, а не расширяет её.
6. WHEN обновляются название и описание клуба, сервис MUST отдавать ту же модель ответа, что и остальные операции над клубом - с владельцем, жанрами и счётчиками.
7. `members_count` в ответе и `total` страницы участников MUST браться из столбца загруженного клуба. Сервис MUST NOT считать участников агрегатом: стоимость такого счёта росла с размером клуба, а не страницы, и на каталоге умножалась на число клубов страницы.
8. Карточка клуба MUST содержать текущий заход - книгу, дедлайн и долю участников в графике - либо пустое значение, если клуб ничего не читает. Данные захода MUST собираться батчем на всю страницу клубов, как владелец и жанры.
9. WHEN создаётся заход или номинируется книга, книга MUST резолвиться через `BooksPort.get_or_create_book` по тому же идентификатору тома, что и у тредов: повторный выбор той же книги MUST переиспользовать запись.
10. Создавать и закрывать заход, а также закрывать голосование MUST только владелец клуба (или админ) - через ту же проверку прав, что и остальные операции владельца. Ролей модератора в домене пока нет.
11. Отмечать прогресс MUST только участник клуба и только пока заход не закрыт. Отметка MUST заменять прогресс целиком: прислан этап - фиксируется он, прислана только страница - закрытым считается последний этап, чья последняя страница уже прочитана.
12. Участник считается в графике, когда его закрытый этап не ниже последнего этапа, чей срок уже наступил. WHILE ни один срок не наступил, в графике MUST считаться все участники клуба, включая не отметивших ничего - отставать не от чего.
13. Доля участников в графике MUST считаться от числа участников клуба, а не от числа отметившихся, и MUST NOT превышать единицу.
14. Сводка текущего захода MUST содержать этап, который должен быть закрыт к сегодняшнему дню; пока ни один срок не наступил - пустое значение.
15. Номинировать книгу и голосовать MUST только участник клуба: книгу клубу выбирают те, кто его читает.
16. Номинация в ответе MUST содержать число голосов и признак «за неё отдан голос текущего пользователя». Число голосов MUST считаться на чтение, а не храниться счётчиком.
17. WHEN участник голосует, его прежний голос в этом клубе MUST переставляться на новую номинацию, а не добавляться вторым. Повторный голос за ту же номинацию MUST быть идемпотентен по числу голосов.
18. WHEN владелец закрывает голосование, победителем MUST становиться номинация с наибольшим числом голосов, при равенстве - номинированная раньше. Из книги победителя MUST создаваться заход клуба по присланным срокам и этапам - тем же путём, что и заход, заведённый вручную.
19. WHEN голосование закрыто, номинации и голоса клуба MUST очищаться: следующее голосование начинается с чистого листа, а выбранная книга живёт дальше как заход.
20. Заход MUST создаваться до очистки номинаций: если у клуба уже есть незакрытый заход, закрытие голосования MUST оставить номинации и голоса нетронутыми.
21. Число кандидатов в клубе MUST быть ограничено потолком: список номинаций отдаётся клиенту целиком, без страниц, и без потолка один участник мог бы завалить экран клуба тысячей книг. Потолок MUST проверяться счётом кандидатов, а не загрузкой списка.

## Constraints & Invariants
- Инвариант: сервис не импортирует модули iam/genres/threads напрямую - только порты и события.
- Инвариант: `threads_count` клуба - денормализованный столбец, изменяется только обработчиками событий THREAD_CREATED/THREAD_DELETED, не пользовательскими операциями.
- Инвариант: `members_count` - тоже денормализованный столбец, но своего домена: его ведёт репозиторий в одной транзакции с club_members, событий для него нет.
- Инвариант: название и описание клуба редактируются только владельцем и только через `update_book_club`; жанры - отдельной операцией `set_genres`.
- Инвариант: текущий заход у клуба один; следующий можно завести только после закрытия предыдущего.
- Инвариант: доля участников в графике и число голосов номинации - производные величины, они нигде не хранятся и считаются на чтение.
- Инвариант: у участника один голос на клуб, и переставить его можно только на другую номинацию того же клуба.
- Ограничение: потолок кандидатов - защита от заваленного списка, а не инвариант. Две параллельные номинации на границе могут дать на одну больше, и это допустимо; персональной квоты на участника нет.

## Failure Behavior
1. IF среди кодов жанров есть неизвестный, THEN сервис MUST выбросить UnprocessableEntity с перечнем неизвестных кодов. Это правило распространяется и на коды жанров в запросе поиска: неизвестный код - ошибка, а не молча пустая выдача.
2. IF клуб не найден, THEN сервис MUST пробросить NotFound репозитория.
3. IF `owner_id` клуба NULL (владелец удалил аккаунт без удаления клубов), THEN ответ MUST содержать `owner = null`; такой клуб через API удалить и отредактировать нельзя - принятое ограничение, проверка владельца не проходит ни для кого. Голосование в таком клубе тоже не закрыть.
4. IF у клуба нет незакрытого захода, THEN запрос текущего захода MUST вернуть NotFound, а не пустую сводку.
5. IF присланный этап принадлежит другому заходу, THEN отметка прогресса MUST вернуть NotFound.
6. IF прогресс отмечает не участник клуба, THEN сервис MUST выбросить Forbidden; IF заход уже закрыт, THEN Conflict.
7. IF номинирует или голосует не участник клуба, THEN сервис MUST выбросить Forbidden.
8. IF в клубе нет ни одной номинации, THEN закрытие голосования MUST выбросить Conflict - заход не из чего создавать.
9. IF снимается голос, которого за эту номинацию не было, THEN сервис MUST выбросить Conflict, а не сообщать об успехе: иначе клиент считает, что голос снят, тогда как он остался на другой номинации.
10. IF список кандидатов клуба полон, THEN номинация MUST вернуть Conflict с указанием, что голосование нужно закрыть.

## Conformance
Реализация конформна, когда выполняет поведения 1-21, держит инварианты портов, обоих счётчиков, единственного текущего захода и единственного голоса участника и правила отказов 1-10. Проверяется тестами tests/bookclubs/, tests/readings/ и tests/nominations/.
